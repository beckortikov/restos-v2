# Деплой multi-branch sync (ADR-003, Фаза 3)

Как поднять сеть филиалов: центральный узел + филиалы. **Выбранный путь — центр
на VPS** (публичный HTTPS, без туннеля; модель iiko). Вариант «центр на кассе +
туннель» — как альтернатива ниже. Код — Фазы 1/2/4
(см. [ADR-003](../decisions/ADR-003-multi-branch-network.md)).

> **Практический runbook установки central (с нуля до сети)** —
> [central-install.md](central-install.md). Этот файл — справочник по
> механизму; для «поставить и подключить» идти туда.

> **Быстрый путь (ADR-003, продолжение).** Ручные шаги ниже (бутстрап через
> браузер, env/UI-настройка на каждом филиале) не обязательны построчно —
> `server/scripts/setup-central.sh` делает весь central одним прогоном и
> печатает готовый код приглашения; на филиале этот код вставляется ОДНИМ
> полем на странице Настройки → Синхронизация — адрес/секрет/account_id
> подставляются сами, без SQL и без переменных окружения на филиале.
> Подключение применяется **сразу, без перезапуска кассы** (пушер/пуллер
> перечитывают `sync_settings` на каждом тике, не один раз при старте).
> Инструкция ниже остаётся справочником по самому механизму (что на самом
> деле происходит под капотом) и как fallback для нестандартных случаев
> (например, туннель вместо публичного адреса).

## Роли узлов

- **Центральный узел** — одна установка `restos-server`, куда стекаются данные
  всех филиалов (обычно на главной кассе / центральном складе). Принимает
  `/sync/ingest`, отдаёт `/sync/pull`. Владелец смотрит сводку и отчёты здесь.
- **Филиал** — обычная касса. Работает **автономно** на своей БД; в фоне пушер
  отправляет свои дельты (перемещения, финопы) на центральный узел и тянет
  входящие перемещения.

Оба — тот же бинарь `restos-server`, разница только в конфиге.

# Рекомендуемо: центральный узел на VPS (модель iiko) ✅

**Выбранный путь.** Центр на арендованном сервере (VPS) с публичным HTTPS —
всегда онлайн, публично адресуем, кассы шлют **исходящий** sync. **Туннель НЕ
нужен** (у VPS белый IP; кассы — клиенты, им публичный адрес не нужен). Это
архитектура iiko, только self-hosted. Плюс это готовый фундамент под будущее
клиентское приложение (гости заказывают → см. ADR-004, когда появится).

```
[Кассы кафе] ──исходящий HTTPS──▶ [VPS: restos-server (central) + Caddy + Postgres]
  локально, офлайн-устойчиво         публичный, 24/7, домен central.example.com
```

## Шаг 1. VPS

- Небольшой VPS (~$5–10/мес, ~2 ГБ RAM), в **ближайшем регионе** (быстрее sync и
  будущее приложение гостей).
- Домен → A-запись на IP VPS (напр. `central.moyaset.ru`).

## Шаг 2. restos-server в роли центра

Запустить `restos-server` на VPS (слушает `127.0.0.1:3002`, наружу — через Caddy):
```
RESTOS_HTTP_ADDR=127.0.0.1:3002
RESTOS_SYNC_TOKEN=<общий-секрет-сети>     # тем же секретом ходят кассы
# external Postgres на этом же VPS (или embedded) — как в основном деплое
```

## Шаг 3. Caddy — авто-HTTPS реверс-прокси

`/etc/caddy/Caddyfile`:
```
central.moyaset.ru {
    reverse_proxy 127.0.0.1:3002
}
```
Caddy сам получит Let's Encrypt-сертификат. Всё, центр доступен по
`https://central.moyaset.ru`.

> Можно проксировать только `/sync/*`, `/api/v1/network/*` и `/healthz`, а
> админский UI/эндпоинты не выставлять — тогда наружу торчит лишь нужное.

## Шаг 4. Конфиг касс (филиалов)

```
RESTOS_SYNC_ENABLED=true
RESTOS_SYNC_CENTRAL_URL=https://central.moyaset.ru
RESTOS_SYNC_TOKEN=<общий-секрет-сети>
RESTOS_SYNC_RESTAURANT_ID=<id этого филиала>
RESTOS_SYNC_INTERVAL_SEC=30
```

Кассы работают локально; в фоне шлют исходящий HTTPS на VPS. **Лагов нет** —
POS живёт на localhost, sync асинхронный (см. ADR-003).

## Шаг 5. Проверка
```bash
curl https://central.moyaset.ru/healthz            # с любой машины
# с кассы — логи: sync pusher started / sync puller started
```

Дальше — «Общий секрет сети», «Завести сеть», «Проверка» ниже.

# Альтернатива: центральный узел на кассе + туннель

Если VPS не берём и центр — главная касса (за NAT, без белого IP), нужен туннель.

## Туннель (Tailscale)

1. Зарегистрировать tailnet, поставить Tailscale на все машины (центр + филиалы).
2. `tailscale up` на каждой — получить их 100.x.y.z адреса.
3. Проверить: с филиала `curl http://<central-tailscale-ip>:3002/healthz`.
   `RESTOS_SYNC_CENTRAL_URL=http://<central-tailscale-ip>:3002`.

Альтернативы туннелю: **Cloudflare Tunnel** (`cloudflared` на кассе — публичный
адрес без белого IP, бесплатно), **WireGuard** (вручную, нужен достижимый центр).

> **Важно:** этот вариант — центр доступен, только пока касса включена (сводка
> владельцу тоже). Для 24/7 и клиентского приложения — VPS (см. выше). Переезд
> дешёвый: меняется только `RESTOS_SYNC_CENTRAL_URL`.
> Для 24/7 — вынести центральный узел на VPS (тот же бинарь, тот же конфиг,
> меняется только адрес). Филиалы при этом остаются офлайн-устойчивыми.

## Шаг 2. Общий секрет сети

Придумать один секрет на всю сеть (например, `openssl rand -hex 32`). Он должен
совпадать на центральном узле и на всех филиалах.

## Шаг 3. Конфиг центрального узла

Центр только **принимает** sync — ему нужен лишь секрет:

```
RESTOS_SYNC_TOKEN=<общий-секрет-сети>
```

`/sync/*` откроется только с этим токеном (иначе 401). Пушер на центре не нужен.

## Шаг 4. Конфиг филиала

Филиал **пушит вверх и тянет вниз**:

```
RESTOS_SYNC_ENABLED=true
RESTOS_SYNC_CENTRAL_URL=http://<central-tailscale-ip>:3002
RESTOS_SYNC_TOKEN=<общий-секрет-сети>          # тот же, что на центре
RESTOS_SYNC_RESTAURANT_ID=<id этого филиала>    # для pull входящих перемещений
RESTOS_SYNC_INTERVAL_SEC=30                      # период пуша/тяги (по умолчанию 30)
```

`RESTOS_SYNC_RESTAURANT_ID` — id ресторана этого филиала в его БД (down-sync
тянет перемещения, адресованные именно ему). Без него работает только up-push.

### Два пути конфигурации (env vs UI/БД)

Sync-настройки читаются из **двух источников**:

1. **UI → БД** (основной для десктоп-кассы, где есть оператор). Настройки →
   **Синхронизация** пишет их в таблицу `sync_settings` (singleton, id=1). Go-бэк
   читает эту таблицу при старте (в `cmd/restos-server/main.go`, после миграций) —
   значения из БД **переопределяют** env на старте, ЕСЛИ строка уже существовала.
   Но применяется изменение сразу, БЕЗ рестарта кассы: Pusher/Puller перечитывают
   `sync_settings` на каждом тике (не один раз при старте), кроме `interval_sec` —
   частота самого тика фиксируется при старте процесса, смена интервала
   применится со следующего перезапуска.
2. **env `RESTOS_SYNC_*`** — для **безоператорных** запусков, где никто не кликает
   Настройки: bootstrap (пока `sync_settings` пуст), **центральный узел на VPS**
   (разворачивается headless через systemd/docker — токен приходит из env юнита),
   CI/интеграционные тесты. Используются, если в `sync_settings` пусто.

> Дело не в наличии UI (React-фронт бэк отдаёт на `:3001` в любой сборке с
> `embed-spa`, а в dev — Vite на `:5173`), а в наличии **оператора**: касса
> настраивается через интерфейс, VPS-центр и тесты — через env.

> Electron (`desktop/main.js`) **не пробрасывает** `RESTOS_SYNC_*` в спавнящийся
> бинарь и не должен: на кассе конфиг вводится в UI и живёт в БД, Go читает его
> сам. Env-путь — только для запуска сервера напрямую без десктоп-обёртки.

## Шаг 5. Завести сеть

1. На **центральном узле** в UI: Настройки → **Филиалы сети** → «Создать сеть».
   Текущий ресторан станет центральным складом (`kind=central_warehouse`).
2. Филиалы присоединяются к сети своим `account_id`. В v4 он приходит из
   license-токена (`payload.aid`) при активации — выдать филиалам лицензии с тем
   же `aid`, что у сети. (Пока лицензирование сети не автоматизировано — можно
   проставить `restaurants.account_id` вручную в БД филиала.)
3. Номенклатуру завести в UI (Склад → Номенклатура сети) и привязать ингредиенты.

## Шаг 6. Проверка

- Филиал → Склад → **Перемещения** → создать перемещение на другой филиал.
- Через ~интервал на центральном узле в БД появится `stock_transfers` (up-sync).
- На филиале-получателе через pull появится входящее перемещение → принять.
- Владелец на центре: Финансы → **Сводка по сети** — выручка по филиалам;
  `BranchSelector` в шапке — смотреть любой отчёт по конкретному филиалу.

## Диагностика

- `curl -H "Authorization: Bearer <секрет>" http://<central>:3002/api/v1/sync/pull?restaurant_id=<id>`
  — должен вернуть `{entries:[...]}` (или пусто). 401 → не совпал секрет.
- Логи филиала: `sync pusher started` / `sync puller started`, `sync push failed`
  (если центр недоступен — филиал продолжает работать автономно).
- `sync_log` на филиале: строки с `synced_at IS NULL` — ещё не отправлены.
