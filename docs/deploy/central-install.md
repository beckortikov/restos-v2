# Установка центрального узла сети (runbook)

Пошаговая инструкция «с нуля до работающей сети»: поднять central, подключить
первый филиал, обновлять и чинить. Механизм синка и нестандартные схемы
(туннель, env-конфигурация) — в справочнике
[multi-branch-sync.md](multi-branch-sync.md); архитектура — в
[ADR-003](../decisions/ADR-003-multi-branch-network.md).

**Установщик один.** Отдельного «central-установщика» нет: роль узла — это
данные, а не сборка. Windows-касса становится центром кнопкой «Создать сеть»,
филиалом — вводом кода приглашения. На VPS ставится тот же Go-бинарь, только
собранный под Linux.

Два варианта размещения центра:

| | **А. VPS (рекомендуемый)** | **Б. Центр — обычная касса** |
|---|---|---|
| Что ставится | `restos-server-linux-amd64` + systemd + Caddy | Обычный exe-установщик |
| Доступность | 24/7, публичный HTTPS | Пока касса включена |
| Филиалы ходят | Через интернет, из любой точки | Только LAN или туннель (Tailscale) |
| Кому подходит | Сеть точек в разных местах (модель iiko; так живёт Macburger) | Все точки в одном здании / пилот |

## Вариант А. Central на VPS

### Что понадобится

- VPS ~2 ГБ RAM, Ubuntu 22.04/24.04, в ближайшем к точкам регионе (~$5–10/мес).
- Домен с A-записью на IP VPS (например `central.moyaset.ru`).
- Локально собранный бинарь (шаг 2).

### Шаг 1. Создать VPS (cloud-init)

При создании VPS вставить в поле «Cloud-init» содержимое
[server/scripts/cloud-init-central.yaml](../../server/scripts/cloud-init-central.yaml),
**заменив SSH-ключ на свой**. Он сразу даёт: вход по ключу под root, firewall
(только 22/80/443), fail2ban. Если провайдер без cloud-init — сделать то же
руками (`ufw allow OpenSSH && ufw allow 80,443/tcp && ufw enable`,
`apt install fail2ban`).

Сам бинарь через cloud-init доставить нельзя (лимит user-data ~16–64 КБ,
бинарь ~37 МБ) — он заливается на шаге 3.

### Шаг 2. Собрать бинарь (локально)

```bash
cd server && make build-all
```

Нужный файл — `server/bin/restos-server-linux-amd64`.

### Шаг 3. Залить на VPS

```bash
ssh root@<IP> 'mkdir -p /opt/restos'
scp server/bin/restos-server-linux-amd64 root@<IP>:/opt/restos/restos-server
scp server/scripts/setup-central.sh root@<IP>:/opt/restos/
ssh root@<IP> 'chmod +x /opt/restos/restos-server /opt/restos/setup-central.sh'
```

### Шаг 4. Caddy (HTTPS)

Пакета `caddy` нет в дефолтных репозиториях Ubuntu — подключить репозиторий
Caddy (актуальная команда: [caddyserver.com/docs/install](https://caddyserver.com/docs/install#debian-ubuntu-raspbian)),
затем:

```bash
apt install caddy
```

`/etc/caddy/Caddyfile`:

```
central.moyaset.ru {
    reverse_proxy 127.0.0.1:3002
}
```

`systemctl reload caddy` — сертификат Let's Encrypt Caddy получит сам
(A-запись уже должна указывать на VPS). Наружу торчит только 443; порт 3002
остаётся локальным.

### Шаг 5. Поднять central одним прогоном

```bash
ssh root@<IP> '/opt/restos/setup-central.sh https://central.moyaset.ru "Моя сеть" 1234'
```

Аргументы: публичный адрес, название сети, PIN владельца (не указать —
сгенерируется случайный). Скрипт сам:

1. заводит systemd-юнит `restos-central-org-3002` (автозапуск, рестарт при
   падении) под системным пользователем `restos` — embedded Postgres не
   работает под root;
2. кладёт секрет сети в `/etc/restos-central-org-3002.env` (0600, не в юните —
   юниты world-readable);
3. бутстрапит ресторан «Моя сеть», создаёт сеть (этот узел —
   `central_warehouse`);
4. печатает **PIN владельца** и **готовый код приглашения** для первого
   филиала.

Сохранить и то и другое. Скрипт идемпотентен: повторный прогон на уже
инициализированном сервере ничего не создаёт заново.

### Шаг 6. Подключить филиал

На кассе филиала: **Настройки → Синхронизация → «Код приглашения»** — вставить
строку из шага 5. Адрес, секрет и account_id подставятся сами; перезапуск кассы
не нужен (пушер/пуллер перечитывают настройки на каждом тике). Ещё коды —
на центральном узле: **Настройки → Филиалы сети → Приглашения**.

Филиал работает автономно на своей БД; при обрыве интернета копит дельты и
дошлёт их сам, когда связь вернётся.

### Шаг 7. Проверить

```bash
curl https://central.moyaset.ru/healthz        # {"status":"ok",...}
ssh root@<IP> journalctl -u restos-central-org-3002 -n 50
```

На кассе филиала: **Настройки → Синхронизация** — виджет очереди
(отправлено/в очереди/ошибки). На central в браузере
(`https://central.moyaset.ru`) под владельцем: **Финансы → Сводка по сети** —
филиал появился.

### Несколько организаций на одном VPS

Один бинарь — много независимых сетей. Каждой — свой PORT (и всё остальное
скрипт разведёт сам: юнит, data-dir, env-файл, порт embedded Postgres):

```bash
PORT=3003 INSTANCE=pizza-tashkent /opt/restos/setup-central.sh https://pizza.example.com "Пицца"
```

В Caddyfile — второй блок с `reverse_proxy 127.0.0.1:3003`. Скрипт сам
откажется запускаться, если PORT уже занят другой организацией.

### Обновление бинаря на VPS

Central не обновляется авто-апдейтом (это не Electron) — руками:

```bash
cd server && make build-all
scp server/bin/restos-server-linux-amd64 root@<IP>:/opt/restos/restos-server.new
ssh root@<IP> 'systemctl stop restos-central-org-3002 && \
  mv /opt/restos/restos-server.new /opt/restos/restos-server && \
  chmod +x /opt/restos/restos-server && \
  systemctl start restos-central-org-3002'
```

Бинарь общий для всех организаций на VPS — остановить/запустить надо **каждый**
юнит (`systemctl list-units 'restos-central-*'`). Миграции накатятся сами при
старте. Порядок обновления сети: **сначала central, потом кассы** — новые кассы
могут слать сущности, которых старый central не знает; наоборот безопасно.

### Бэкапы

Ежедневный `pg_dump --format=custom` в 3:00 → `$DATA_DIR/backups`
(по умолчанию `/opt/restos/org-3002/data/backups`), ротация 7 дневных +
4 недельных + 12 месячных. Рекомендуется дополнительно копировать этот каталог
с VPS (rclone/restic/бэкап провайдера) — VPS тоже умирают.

### Частые проблемы

| Симптом | Причина и что делать |
|---|---|
| `process already listening on port 54330` | Второй инстанс без своего `PG_PORT` (скрипт новых версий разводит сам) либо осиротевший Postgres: `pkill -f 'pg-runtime'` и `systemctl restart` юнита. |
| Каса пишет `sync push 401` | Секрет не совпадает, либо филиал **отключён от сети** (detach обнуляет account_id — персональный токен получает 401). Переподключить кодом приглашения. |
| `sync push 5xx`, очередь растёт | Central лежит/не достижим. Данные не теряются: после 3 неудач батча пушер изолирует «ядовитую» строку и продолжает; остальное дошлётся. Смотреть виджет очереди и `journalctl` на VPS. |
| Товар создан на central, у филиала нет | Подождать тик синка (30 с); проверить, что у филиала включена синхронизация и виджет очереди без ошибок. |
| Повторный прогон скрипта: «уже отвечает ДРУГАЯ организация» | На этом PORT живёт чужой инстанс — задать свободный `PORT=` и `INSTANCE=`. |

## Вариант Б. Центр — обычная касса (exe)

Когда все точки в одном здании (или это пилот) и отдельный сервер не нужен.

1. Поставить **обычный exe-установщик** на машину, которая будет центром
   (обычно главная касса / склад). Никакого специального дистрибутива.
2. Под владельцем: создать сеть (**Настройки → Филиалы сети**) — узел
   становится `central_warehouse`.
3. Там же сгенерировать код приглашения и ввести его на кассах филиалов
   (**Настройки → Синхронизация**).
4. Филиалы должны сетево достучаться до центра:
   - в одном LAN — код приглашения генерировать с адресом
     `http://<IP-центра>:3002`;
   - в разных местах без VPS — туннель (Tailscale), см.
     [multi-branch-sync.md](multi-branch-sync.md), раздел «Альтернатива».

Ограничения честно: центр доступен, только пока эта касса включена; выключили
на ночь — филиалы копят очередь (не теряют, дошлют утром). Для сети из
нескольких заведений в разных местах — вариант А.

## Куда смотреть дальше

- Отключить филиал от сети / убрать приглашение: **Настройки → Филиалы сети**
  (данные филиала на central сохраняются; повторное подключение возвращает всё).
- Что реплицируется и в какую сторону, конфликт-правила, офлайн-поведение:
  [ADR-003](../decisions/ADR-003-multi-branch-network.md).
- Деньги/расходы за филиалы, зарплата из центра: страницы **Финансы →
  Переводы в сети / Расходы за филиалы / Персонал сети** (доступны на central).
