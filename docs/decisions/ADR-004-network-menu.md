# ADR-004 — Сетевое меню: общая база + переопределения по филиалу

**Status:** Proposed
**Date:** 2026-07-01
**Deciders:** owner
**Ветка:** `feat/multi-branch-network`
**Связано:** [ADR-003](ADR-003-multi-branch-network.md) (сеть филиалов, sync, номенклатура 3B)

## Контекст

Сеть филиалов ([ADR-003](ADR-003-multi-branch-network.md)) уже даёт: перемещения,
общую **номенклатуру** ингредиентов (3B), сводку владельцу, sync. Меню при этом
осталось **пер-ресторанным** (`menu_items.restaurant_id`) — у каждого филиала
своё, независимо. Для сети это неудобно: нет единого управления, дубли, при
изменении блюда его правят в каждой точке отдельно.

Решение по модели (принято owner): **общая база + переопределения по филиалу**
(как в iiko) — не «жёстко общее» и не «полностью независимое».

Мотивация также — будущее клиентское приложение (ADR-005, когда появится): гость
выбирает кафе и видит **его** цены/доступность, но каталог блюд — общий по сети.

## Решение

**Мастер-меню на уровне сети (`account_id`) + наследование филиалами + локальные
переопределения.** Мастер живёт на центральном узле, распространяется в филиалы
через существующий sync (down-pull, как перемещения). Локальные правки филиала
**не затираются** обновлением мастера.

### Разделение полей (детерминированный merge)

| Поле | Источник | При обновлении мастера |
|---|---|---|
| name, category, station, unit, техкарта, base cogs | **мастер** | перезаписывается |
| base_price | мастер | дефолт при создании; дальше — локальное |
| **price** | **филиал** | не трогается |
| **is_available / стоп** | **филиал** | не трогается |
| emoji, фото, sort_order | филиал | не трогается |

- **Наследуемые** поля (что за блюдо, из чего готовится) — из мастера, едины по сети.
- **Локальные** поля (цена, доступность, оформление) — у филиала свои, мастер их
  не перезаписывает.
- **Локальное блюдо** (`master_id = NULL`) — полностью принадлежит филиалу
  (местный специалитет), в мастере его нет.

Это тот же принцип, что номенклатура 3B: общий ключ (`master_id`) связывает «одно
блюдо» между филиалами, но количественно-локальные атрибуты у каждого свои.

## Слой данных

| Миграция | Содержание |
|---|---|
| `0NN_network_menu.sql` | Таблица `network_menu_items` (account-level мастер: `id`, `account_id`, `name`, `category`, `base_price`, `station`, `unit`, `emoji`, техкарта-ref) + `menu_items.master_id` (nullable, FK-ish на мастер) |

Номер миграции — следующий свободный на момент реализации.

## Sync

- Мастер-меню редактируется **на центральном узле** (владельцем) → распространяется
  **вниз** в филиалы. Расширяем down-pull: филиал тянет `network_menu_items` своей
  сети и применяет:
  - нет локального `menu_items` с этим `master_id` → создать (наследуемые поля из
    мастера, `price = base_price`, `is_available = true`);
  - есть → обновить **только наследуемые** поля, локальные (price/availability/
    оформление) не трогать.
- Локальные блюда филиала (`master_id = NULL`) вверх на центр можно НЕ синкать
  (они не часть мастера) — либо синкать для сводного каталога (реши при
  реализации; MVP — не синкать).

## Эндпоинты (эскиз)

- `GET /api/v1/network/menu` — мастер-меню сети.
- `POST /api/v1/network/menu` — создать блюдо в мастере.
- `PATCH /api/v1/network/menu/{id}` — править мастер (name/category/price/техкарта).
- (down-pull мастера — через существующий `/sync/pull`, расширенный на
  `network_menu_items`).
- Существующие `menu_items`-эндпоинты филиала — без изменений: филиал правит
  цену/стоп/локальные блюда как сейчас.

## Фронт (эскиз)

- **Центр:** экран «Меню сети» — CRUD мастер-меню (владелец/менеджер сети).
- **Филиал:** существующий экран меню — показывает наследованные блюда (из
  мастера, наследуемые поля read-only или с пометкой «из сети») + локальные;
  филиал меняет цену/доступность, добавляет локальные блюда.
- Индикатор «из сети» / «локальное» на карточке блюда.

## Последствия

### Положительные
- Единое управление ассортиментом сети; изменил блюдо/техкарту в мастере —
  разъехалось по всем.
- Локальная гибкость: цены и стоп по каждому кафе, местные блюда.
- Готовый фундамент для клиентского приложения (гость видит меню конкретного кафе).
- Переиспользует sync-механизм ADR-003 (down-pull + merge с сохранением локального).

### Отрицательные
- Заметный объём (мастер + merge + распространение + два UI) — сравнимо с
  номенклатурно-перемещенческой частью ADR-003.
- Merge наследуемое/локальное надо аккуратно тестировать (чтобы обновление мастера
  не сбросило локальную цену/стоп).
- Техкарты блюд ссылаются на ингредиенты, а те пер-филиальные (3B) — при
  распространении мастер-техкарты в филиал ингредиенты резолвятся по
  `nomenclature_id` (как в перемещениях). Учесть при реализации.

## Фазы реализации

1. **Данные:** миграция `network_menu_items` + `menu_items.master_id`, модели.
2. **Мастер CRUD:** сервис + эндпоинты `/network/menu` + экран «Меню сети» (центр).
3. **Распространение:** расширить down-pull на мастер-меню + merge (наследуемое из
   мастера, локальное сохраняется); техкарта резолвится по номенклатуре.
4. **Филиал UI:** пометки «из сети/локальное», разрешить локальные переопределения.

## Открытые вопросы

- **Техкарты в мастере vs пер-филиал** — мастер хранит техкарту в терминах
  номенклатуры сети; филиал резолвит в свои ингредиенты по `nomenclature_id`.
  Уточнить, кто «авторитет» по техкарте (сеть) и можно ли филиалу её менять.
- **Синк локальных блюд вверх** — нужен ли сводный каталог всех блюд сети на
  центре (для аналитики), или локальные остаются только в филиале. MVP — только
  в филиале.
- **Категории** — общие по сети или свободный текст (как сейчас). Логично увязать
  с мастером.
