# ADR-003 — Сеть филиалов: локальная БД на филиале + sync на центральный узел

**Status:** Accepted — Фазы 1–4 реализованы (2026-07-01); настройка туннеля — на месте (см. deploy-гайд)
**Date:** 2026-06-19
**Deciders:** owner
**Ветка:** `feat/multi-branch-network`

## Контекст

Появилась потребность объединить несколько ресторанов одного владельца в **сеть филиалов**:

1. **Центральный склад.** Основной закуп оптом идёт в один склад, оттуда товар **перемещается** по филиалам.
2. **Перемещения между филиалами** — учитываемая операция (расход на источнике, приход на получателе), а не ручная сверка.
3. **Сводка владельцу** — owner видит показатели **всей компании** и **по каждому филиалу** отдельно.

Текущая архитектура v4 (см. [ADR-001](ADR-001-go-stack.md)) — автономная: **один Go-бэк + один embedded PostgreSQL на машину кассира**, без облака ([07-FUTURE-CLOUD.md](../prd/07-FUTURE-CLOUD.md)). Это и есть главное ограничение: данные филиалов физически на разных машинах, общего места для запроса «по всей сети» нет.

### Как это решают другие (iiko) — для ориентира

iiko решает задачу **централизацией**: терминалы (iikoFront) ходят на сервер (iikoServer) внутри точки, а для сети есть отдельный центральный слой **iikoChain** (центральный склад/закуп, внутренние перемещения, консолидированная отчётность), куда всё стекается. То есть «единый склад сети + сводка в реальном времени» у них требует постоянно живого центрального сервера. Это именно тот компонент, которого в v4 нет.

### Развилки, которые проговорили

- **Топология:** облако / хаб (главная касса) / только локально+ручная сверка.
- **Офлайн:** должен ли филиал работать без связи с центром.
- **Где центральный узел:** на главной кассе или на выделенном VPS.

Принятые ответы: **филиал обязан работать офлайн**; центральный узел **пока на главной кассе**; владельцу нужна сводка по всей сети.

> Ключевой вывод обсуждения: требования «филиал работает офлайн» + «сводка по всей сети» **взаимоисключают чистый хаб** (одна общая БД). Офлайн ⇒ у каждого филиала обязана быть **своя локальная БД** ⇒ значит нужен **слой синхронизации** на центральный узел. Это не хаб и не «просто туннель» — это распределённая система с sync. Туннель — лишь транспорт.

## Решение

**Каждый филиал (включая центральный склад) остаётся автономным узлом v4** — свой Go-бэк + свой embedded PostgreSQL, как сейчас (офлайн-устойчивость сохраняется). Поверх добавляется:

1. **Понятие сети (`account`)** — несколько ресторанов группируются под одним `account_id` (колонка уже заведена миграцией 009, заполняется из license-токена `aid`).
2. **Центральный узел** — отдельный экземпляр того же Go-бэка, собирающий данные всех филиалов. **Пока размещается на главной кассе**, доступен филиалам через **туннель** (Tailscale/WireGuard — приватная VPN, без проброса портов и статического IP).
3. **Слой синхронизации** — каждый филиал асинхронно пушит **свои** изменения на центральный узел; центр раздаёт «общие» сущности (меню/техкарты, входящие перемещения) вниз.
4. **Перемещения** — пара движений `transfer_out`/`transfer_in`, доезжающих между узлами через sync (eventually consistent).
5. **Сводка владельцу** — читается с центрального узла (real-time по собранным данным).

Туннель нужен **для перемещений и для сводки владельцу**; для собственной работы филиала (продажи) он не требуется.

## Обоснование

### Почему локальная БД на филиале (а не чистый хаб)

Чистый хаб (терминалы филиала ходят в одну БД на главной кассе) проще, но:
- филиал **не работает без связи** — для общепита неприемлемо (продажи встанут при обрыве интернета/перезагрузке главной кассы);
- каждое действие POS — round-trip по интернету, ощутимая задержка.

Локальная БД сохраняет принцип ADR-001 (офлайн-first) и убирает задержки на горячих путях (заказы, оплата идут к localhost).

### Почему sync почти без конфликтов

В обычном multi-master ад — конфликты записи. У нас их почти нет благодаря **`restaurant_id` на каждой строке**:

- каждый филиал — **единственный писатель своих строк** (свои заказы, свой склад, свои смены);
- sync практически односторонний по партиции: филиал → центр (свои данные), центр → филиал (общие справочники + адресованные ему перемещения);
- сводить конкурентные правки одной строки не нужно.

Это ровно те «бесплатные» заделы, которые PRD 07 просил держать: UUID-ключи, `updated_at`, `restaurant_id`, `idempotency_keys` — всё уже в схеме.

### Почему центральный узел = тот же Go-бэк

Центральный узел — не новый продукт, а **тот же бинарь** `restos-server`, запущенный в роли агрегатора (несколько `restaurant_id` одного `account_id` в его БД). Один контракт REST, одни модели, одни миграции. «Хаб на кассе» vs «VPS» отличается **только адресом узла в конфиге**, не кодом.

### Почему центральный узел пока на главной кассе

Ноль дополнительной инфраструктуры на старте. Осознанная плата: **сводка владельцу доступна только пока главная касса включена** (филиалы при этом офлайн-устойчивы — у них своя БД). Перенос узла на VPS (живёт 24/7) — изменение конфига, без переписывания. См. «Открытые вопросы».

## Архитектура изменения

### Топология

```
        ┌─────────────── туннель (Tailscale/WireGuard) ───────────────┐
        │                                                              │
[Филиал A: Go-бэк + local PG]        [Центральный склад / главная касса]
   POS работает на localhost           [Go-бэк роль=central + local PG]
   push своих дельт ──────────────────▶  агрегирует все restaurant_id
                                          одного account_id
[Филиал B: Go-бэк + local PG]                    │
   push своих дельт ──────────────────▶          ▼
                                          [Сводка владельцу]
                                          read по всей сети
```

- Узел сети идентифицируется `account_id`; филиал — `restaurant_id` (как сейчас).
- Центральный склад — это ресторан с `kind = central_warehouse` (склад без зала).

### Слой данных (БД)

Новые миграции в `server/internal/db/migrations/` (актуальная последняя миграция в main — `025`, поэтому новые начинаются с `026`):

| Миграция | Содержание |
|---|---|
| `026_company_accounts.sql` | Таблица `company_accounts` (сеть): `id`, `name`, владелец. FK `restaurants.account_id → company_accounts.id` (колонка `account_id` уже есть с миграции 009). |
| `027_restaurants_kind.sql` | `restaurants.kind` ∈ {`outlet`, `central_warehouse`} (CHECK-constraint, DEFAULT `outlet`). |
| `028_stock_transfers.sql` | `stock_transfers` (`account_id`, `from_restaurant_id`, `to_restaurant_id`, `status`, `transfer_number`, `note`) + `stock_transfer_lines` (`ingredient_id`, `qty`, `cost_per_unit`). |
| `029_nomenclature.sql` | Общий справочник номенклатуры сети (вариант 3B, см. ниже): таблица `nomenclature` (account-level) + `ingredients.nomenclature_id` + `stock_transfer_lines.nomenclature_id`. |
| `030_sync_log.sql` (Фаза 2) | `sync_log` (tracked-таблица, entity, op, payload, `synced_at`) — журнал дельт для пушей. |

> **Уточнение по факту кода (2026-06-30):** отдельная миграция для `stock_movements.type` **не нужна** — колонка `type` объявлена как свободный `TEXT` без CHECK-constraint (см. `001_init.sql`), поэтому значения `transfer_out`/`transfer_in` пишутся как есть. В ADR ранее планировалась лишняя миграция `*_stock_movement_transfer_types` — она удалена.

Денормализация `ingredients.qty` остаётся **только через event-stream `stock_movements`** (правило проекта не нарушается).

#### Сопоставление ингредиентов между филиалами — вариант «3B» (общий ключ)

В текущей схеме `ingredients` привязаны к ресторану (`restaurant_id`), поэтому «Мясо» на центральном складе и «Мясо» в филиале — разные строки с разными `ingredient_id`. Перемещению нужно знать ингредиент **обеих** сторон.

Рассмотренные варианты: (1) явные `from/to ingredient_id` в строке; (2) авто-матч по имени (хрупко); (3) общий каталог номенклатуры на уровне сети (как в iiko). Полный вариант 3 («3A») потребовал бы **вынести остаток `qty` из `ingredients` в пер-филиальную таблицу** — это ~27 файлов бэка и ~16 экранов фронта, читающих остаток, и риск задеть существующие одиночные рестораны.

**Выбран вариант 3B — общий ключ без раскола остатка:**
- `qty` **не трогаем**, `ingredients` остаются пер-ресторанными.
- Добавляется таблица `nomenclature` (account-level: `id`, `account_id`, `name`, `unit`, `category`) — общий справочник продуктов сети.
- `ingredients.nomenclature_id` (nullable) связывает ингредиент филиала с продуктом сети.
- Перемещение хранит `nomenclature_id`; приём находит ингредиент получателя по `(to_restaurant_id, nomenclature_id)`, при отсутствии — создаёт с 0-остатком.
- **Существующие рестораны:** `nomenclature_id = NULL` → ноль изменений, ни один из 27 read-site не трогается. Полный раскол (3A) с экраном остатков по всей сети откладываем до sync-фазы.

### Перемещение (бизнес-логика)

`server/internal/service/stock_transfer.go`:

- `Send()` — в транзакции: `stock_movement{type: transfer_out, qty: -N}` на складе-источнике + статус `sent`. Идемпотентность по `transfer_id`.
- `Receive()` — в транзакции: `stock_movement{type: transfer_in, qty: +N}` на филиале-получателе + статус `received`.
- Между узлами документ доезжает через sync ⇒ перемещение **eventually consistent**: пока филиал офлайн, приход применится при следующей синхронизации.

### Слой синхронизации

`server/internal/cloud/` (заготовка из PRD 07 «Вариант A», активируется здесь):

- `pusher.go` — читает `sync_log`, шлёт дельты на центральный узел (HTTP, тот же REST + `Idempotency-Key`).
- На центральном узле — приём дельт в его БД под нужным `restaurant_id`.
- Раздача общих справочников (меню/техкарты) вниз — отдельным направлением.
- Конфиг: `sync.enabled`, `sync.central_url` (адрес туннеля), `sync.role` = `branch | central`.

### Доступ владельца

`server/internal/repo/base.go`:

- Новый скоуп **`ForAccount(ctx)`** рядом с `ForTenant(ctx)`: для роли `owner` сети → `WHERE account_id = ?` (все филиалы); прочие роли — как сейчас `WHERE restaurant_id = ?`.
- `ForTenant` и существующая логика **не переписываются** (на `ForTenant` завязан CI-линтер).

### Фронт

- `lib/auth-store.tsx` — `account_id` в профиле; право `network.view`.
- `lib/queries/transfers.ts` + новые экраны:
  - `app/(app)/warehouse/transfers/` — список и форма перемещений (форма ≈ клон `receipts/new`, вместо поставщика — выбор филиала).
  - `app/(app)/settings/branches/` — управление филиалами сети (только owner).
- `components/app-sidebar.tsx` — пункт «Перемещения» в раздел «Склад»; раздел/режим «Сеть» для owner.
- Компонент **`<BranchSelector>`** в layout: переключатель «Все филиалы / филиал N» в шапке отчётов `/finance/*` и `/analytics/*` — графики не меняются, меняется скоуп данных.

Существующие складские (13) и финансовые (7) экраны **переиспользуются** — фича добавляет «измерение филиала» поверх готового.

## Последствия

### Положительные

- Филиалы сохраняют офлайн-автономность (принцип ADR-001 не нарушен).
- POS быстрый — горячие пути к localhost, без сетевой задержки.
- Конфликты sync почти отсутствуют (партиционирование по `restaurant_id`).
- Центральный узел = тот же бинарь и контракт; «касса/VPS» — выбор хостинга, не кода.
- Перемещения и центральный склад работают без облака.

### Отрицательные

- **Появляется sync-слой** — заметно больше работы, чем «чистый хаб» или «локально+ручная сверка». Это распределённая система со своими режимами отказа (отставание реплики, повторные доставки).
- **Сводка владельцу доступна только пока главная касса включена** (пока узел на ней). Филиалы при этом работают.
- Перемещения **eventually consistent** — приход на офлайн-филиале появляется с задержкой до синхронизации.
- Зависимость от туннеля (Tailscale/WireGuard) как инфраструктуры.

### Что отказались делать сейчас

- Чистый хаб (одна общая БД) — несовместим с офлайн-требованием.
- Полное двустороннее облако (PRD 07 «Вариант B») — это v5.
- Real-time push-уведомления между филиалами — sync периодический/по событию, не мгновенный.

## Соотношение с другими документами

- **Расширяет** [07-FUTURE-CLOUD.md](../prd/07-FUTURE-CLOUD.md): активирует «Вариант A» (one-way push) раньше, чем «когда сеть >5 точек», но центральный узел — на главной кассе, а не в облаке Supabase.
- **Не противоречит** [ADR-001](ADR-001-go-stack.md): локальный Postgres на филиале сохраняется; центральный узел — тот же Go+PG.
- Не затрагивает [ADR-002](ADR-002-rest-vs-postgrest.md): sync ходит по тому же чистому REST.

> **Реализация (2026-07-01):** Фазы 1, 2, 4 реализованы на ветке `feat/multi-branch-network`. ## Открытые вопросы

- **Перенос центрального узла на VPS** — когда владельцу понадобится сводка 24/7 (сейчас узел на главной кассе ⇒ только пока она включена). Изменение конфига `sync.central_url`, без переписывания.
- **Частота/триггер sync** — по таймеру, по событию (SSE), или гибрид. Уточнить при реализации фазы 2.
- **Лицензирование сети** — одна лицензия на `account_id` или на каждый филиал. Связать с `payload.aid` license-токена.
- **Геораспределённость** — если филиалы окажутся в разных городах с нестабильным интернетом, пересмотреть размещение центрального узла (VPS вместо кассы).
